# Конвейер анализа полногеномных данных при редких наследственных заболеваниях

**Лаборатория молекулярной генетики (МГГ), Северо-Восточный федеральный университет им. М. К. Аммосова, Якутск**

Репозиторий содержит конфигурацию, служебные скрипты и документацию локального конвейера
биоинформатического анализа полногеномного секвенирования (WGS) человека. Конвейер построен на
[nf-core/raredisease](https://nf-co.re/raredisease) 3.1.2 и развёрнут на лабораторных рабочих станциях
под Windows 11 + WSL2. Результаты просматриваются врачом-генетиком в [Scout](https://github.com/Clinical-Genomics/scout).

> В репозитории нет данных пациентов, результатов анализа, референсных баз и учётных данных.
> Коды образцов в комментариях и примерах заменены условными (`SAMPLE01` и т. д.).

---

## 1. Задачи лаборатории

1. **Диагностика редких наследственных заболеваний** у пациентов Республики Саха (Якутия) по данным WGS:
   поиск SNV/инделов, структурных вариантов и CNV, экспансий повторов, вариантов митохондриальной ДНК,
   копийности *SMN1/SMN2*.
2. **Воспроизводимая локальная обработка** без передачи геномных данных во внешние облака: весь анализ
   выполняется на собственных ПК лаборатории.
3. **Формирование популяционной базы якутской когорты** (частоты аллелей SNV и SV по неродственным
   индивидам). Она нужна для фильтрации частых в популяции вариантов, которые отсутствуют или редки в gnomAD.
   Каркас для этого подготовлен (см. раздел 9), включение запланировано после набора когорты.
4. **Масштабирование**: несколько одинаковых рабочих станций, последовательная очередь образцов,
   автоматическая архивация.

## 2. Архитектура

```
FASTQ (MGI/DNBSEQ, PE150, ~30–40x)
  │   C:\NGS_pipeline\new_samples\<код>
  ▼
WSL2 Ubuntu-24.04 + Docker ── nf-core/raredisease 3.1.2 (Nextflow, GRCh38)
  │   fastp → bwa-mem2 → MarkDuplicates → DeepVariant → GLnexus
  │   Manta + TIDDIT + CNVnator → SVDB;  ExpansionHunter/Stranger;  SMNCopyNumberCaller;  MT;  RetroSeq
  │   аннотация: VEP 110 (+ dbNSFP 4.9a, REVEL, SpliceAI, LoFtool, pLI, ClinVar), vcfanno (gnomAD v4.1), CADD 1.7
  │   ранжирование: genmod (стоковые модели Clinical Genomics)
  ▼
/data/raredisease/runs/<код>  ──(rsync + md5)──►  D:\data_annotated\<дата>_<код>_<пол>\{raw,processed}
                                                       │
                                                       ▼
                                         Scout (отдельный WSL-дистрибутив, MongoDB) + IGV
```

## 3. Аппаратная платформа и системная конфигурация

| Компонент | Значение |
|---|---|
| CPU | AMD Ryzen 9 9950X, 16 ядер / 32 потока |
| ОЗУ | 128 ГБ DDR5 (2×64 ГБ); возможен апгрейд до 256 ГБ для параллельного счёта двух образцов |
| Диски | NVMe 4 ТБ (C:, система + WSL ext4.vhdx с референсами и рабочими каталогами); HDD 13 ТБ (D:, архив) |
| ОС | Windows 11, WSL2, Ubuntu 24.04 (пользователь `ngs`), Docker Engine внутри WSL |

Ключевые настройки:

- **`.wslconfig`** (`raredisease-setup/windows/.wslconfig`): `processors=32`, `memory=116GB`, `swap=16GB`.
  Без него WSL получает лишь половину ОЗУ, и этого недостаточно для индекса bwa-mem2.
- **Лимит Nextflow**: 30 CPU / 100 ГБ (`conf/local.config`). Остаток оставлен ОС, Docker и самому Nextflow.
- **Keep-alive**: Windows останавливает WSL при закрытии последнего окна Linux, а вместе с ним и запущенный
  анализ. Скрипт `windows/startup/ubuntu_keepalive.vbs` в автозагрузке держит фоновый процесс WSL.
- Перед долгими прогонами отключаются спящий режим и автоматическая перезагрузка Windows Update.

## 4. Референсные данные (не входят в репозиторий)

Хранятся в `/data/raredisease/references/grch38` (~580 ГБ) и переносятся между ПК клоном WSL (раздел 8).

| Ресурс | Версия / примечание |
|---|---|
| Геном | GRCh38 no-alt analysis set; индексы bwa и bwa-mem2 (сборка индекса bwa-mem2 требует ~90 ГБ ОЗУ) |
| gnomAD | v4.1 genomes, сжат до AF-only VCF для vcfanno (AF, AF_grpmax, AC, nhomalt, AF_eas) и tab-файла для фильтров |
| gnomAD SV | очищен от записей без AF (они ломали SVDB) |
| CADD | 1.7, предрасчитанные SNV + аннотации для инделов (архив 335 ГБ) |
| VEP | кэш 110 merged; плагины dbNSFP 4.9a, REVEL, LoFtool, pLI, ClinVar |
| SpliceAI | маскированные оценки из состава аннотаций CADD, конвертированы `scripts/spliceai_from_cadd.sh` с пересопоставлением символов генов на Ensembl 110 |
| Ранговые модели | стоковые Clinical Genomics (SNV v0.4, SV v0.2) без полей локальных баз (loqusdb, swegen) |

## 5. Распределение ресурсов по процессам

Стоковые ресурсные классы nf-core (`process_medium` 6 CPU / 36 ГБ, `process_high` 12 CPU / 72 ГБ) при
лимите 100 ГБ приводили к последовательному выполнению задач при простаивающем процессоре. Ресурсы
подобраны по фактическим пикам из trace-файлов Nextflow:

| Процесс | Стоково | Настроено | Обоснование |
|---|---|---|---|
| BWAMEM2_MEM | 12 CPU / 72 ГБ | 14 CPU / 40 ГБ | реальный пик ~29 ГБ; две дорожки помещаются параллельно (было 3 ч 48 мин последовательно) |
| SAMTOOLS_MERGE | 2 CPU | 8 CPU | слияние BAM занимало ~1 ч |
| FASTP | 36 ГБ | 4 ГБ | фактически 1,6 ГБ |
| DEEPVARIANT | 12 CPU / 72 ГБ | 24 CPU / 56 ГБ | основной потребитель CPU, ~2 ч на образец |
| GLNEXUS | 12 CPU / 72 ГБ | 12 CPU / 32 ГБ | одиночный образец |
| TIDDIT_SV | 6 CPU / 36 ГБ / 8 ч | `-p 6 --skip_assembly`, 16 ГБ | локальная сборка зависала >7 ч на перицентромерном сателлите chr5 |
| GENMOD (все шаги SNV) | 36 ГБ | 100 ГБ / 24 ч | на ~3 млн SNV OOM-kill приводил к *тихому* зависанию без ошибки |
| CADD | 36 ГБ | 24 ГБ (вспомогательные 2 ГБ) | ~1,5 ядра и 13–15 ГБ на фрагмент |
| ENSEMBLVEP_SNV | 36 ГБ | 16 ГБ | |
| ME_SPLIT_ALIGNMENT, RETROSEQ_DISCOVER | без ограничений | maxForks = 1 | мелкие задачи не дают освободиться 24 CPU для DeepVariant (простой 56 мин) |

**Время обработки** одного WGS (~35–40x): около 10,5–11 ч (до оптимизации 12,5 ч; основные этапы:
DeepVariant ~2 ч, MarkDuplicates ~2 ч, CADD ~3 ч, genmod ~1 ч).

## 6. Хронология внедрения, проблемы и решения

| Этап | Проблема | Решение |
|---|---|---|
| Загрузка референсов | медленный интернет и VPN; CADD доступен только через VPN | gnomAD загружался без VPN, CADD и VEP через VPN по одному; часть gnomAD скачана на втором ПК и перенесена диском; автономные цепочки загрузки (`fetch_hub.sh`) |
| Первый запуск | заготовки «якутских» ранговых моделей и баз (без данных) ломали genmod и SVDB | решено стартовать со стоковых настроек nf-core; якутские компоненты включаются после набора когорты |
| gnomAD SV | записи без AF роняли SVDB | очистка базы |
| Ранжирование SNV | genmod зависал часами после OOM | 100 ГБ на все шаги genmod |
| TIDDIT | зависание на chr5 (8 ч лимит) | `--skip_assembly`; SV остаются от Manta и CNVnator |
| DeepVariant | ошибка `Tmpdir does not exist` при заданном TMPDIR | TMPDIR не переопределяется |
| CADD | torch.hub повторно скачивал ESM-модели | жёсткие ссылки моделей из `esm/` в `checkpoints/` |
| SpliceAI | исходный файл Illumina недоступен | маскированные оценки из аннотаций CADD |
| Scout | падение при загрузке частичных SpliceAI-оценок; Scout молча загружал 0 вариантов без `.tbi` | патч парсера при загрузке (`scout_load.sh`), проверка индексов |
| Архивация | ошибка `Cannot allocate memory` при копировании на D:, пока следующий образец занимал ОЗУ | 4 повтора каждые 20 мин и повтор в конце очереди |
| Производительность | стоковые ресурсы сериализовали задачи | таблица в разделе 5 |

**Валидация**: на контрольных образцах подтверждено обнаружение известной микроделеции (~1,6 Мб, через
TIDDIT/CNVnator) и известного гетерозиготного SNV.

## 7. Эксплуатация

Команда `ngs` (меню `C:\NGS_pipeline\NGS.bat`, инструкция `manual/ngs_guide.html`):

| Команда | Действие |
|---|---|
| `ngs run КОД F/M/U` | запуск образца из `C:\NGS_pipeline\new_samples\КОД` |
| `ngs queue add КОД ПОЛ` / `start` / `stop` / `remove` / `list` | последовательная очередь образцов |
| `ngs status`, `ngs log КОД` | состояние прогонов, место на дисках |
| `ngs resume КОД` | продолжение остановленного прогона (кэш Nextflow) |
| `ngs archive КОД` | повтор архивации после сбоя |
| `ngs discard КОД` | удаление неудачного прогона (с подтверждением) |
| `ngs check` | проверка окружения |

После успешного прогона результаты автоматически копируются в
`D:\data_annotated\<дата>_<код>_<пол>\{raw,processed}`, сверяются по md5 и удаляются с C:.
Выравнивания хранятся в BAM (~46 ГБ на образец) для просмотра в IGV.

Интерпретация ведётся в Scout (институт `nefu_mmhg_arcgen`), см. `scout-setup/README_ru.md`.

## 8. Развёртывание на дополнительной рабочей станции

Рабочие станции одинаковые, поэтому система переносится целиком:

1. Исходный ПК, когда ничего не считается: `second_pc\EXPORT_OLD_PC.bat`. Выполняется `wsl --export`
   (Ubuntu с референсами и Docker-образами, Scout), копия `C:\NGS_pipeline`, `.wslconfig` и keep-alive
   на внешний диск `E:\pc_clone`.
2. Новый ПК: `wsl --install --no-distribution`, перезагрузка, затем `E:\pc_clone\IMPORT_NEW_PC.bat`.
   Скрипт импортирует системы, удаляет прогоны и образцы исходного ПК (чистая сборка) и выполняет `ngs check`.

Обновление скриптов на обоих ПК из этого репозитория:

```bash
cd ~/nefu_mmhg_arctic_genomes_pipeline && git pull
rsync -a raredisease-setup/ ~/raredisease-setup/
bash manual/install_ngs.sh
```

## 9. Планы развития

- Популяционные частоты якутской когорты: GLnexus по gVCF неродственных индивидов
  (`scripts/build_yakut_af.sh`, `build_yakut_svdb.sh`), раздел `[yakut]` в ранговой модели.
  gVCF DeepVariant уже сохраняются для каждого образца.
- Локальная база Loqusdb для учёта частоты вариантов внутри лаборатории.
- Клинический набор генов (OMIM morbid, ~4800 генов) для `generate_clinical_set`.
- Фенотип-ориентированная приоритизация по HPO.
- GATK gCNV после накопления 30–50 геномов для обучения модели.
- Параллельная обработка двух образцов после расширения ОЗУ до 256 ГБ.

## 11. Правила работы с данными

- Имена пациентов не используются в идентификаторах, путях и файлах. Применяются только лабораторные коды.
- Данные и результаты не публикуются в репозитории и внешних сервисах.
- Лицензионные файлы OMIM используются только внутри лаборатории.
- Результаты хранятся на D: (`D:\data_annotated`), на системном диске после архивации не остаются.
