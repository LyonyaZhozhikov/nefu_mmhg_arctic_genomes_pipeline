# Конвейер анализа геномных данных при редких наследственных заболеваниях

**Проект «Геномы Арктики»**

Научно-исследовательская лаборатория «Молекулярная медицина и генетика человека»
Медицинского института ФГАОУ ВО «Северо-Восточный федеральный университет имени М. К. Аммосова» (Якутск)

В репозитории собраны конфигурация, служебные скрипты и документация локального конвейера
биоинформатического анализа данных секвенирования генома человека. Конвейер построен на
[nf-core/raredisease](https://nf-co.re/raredisease) 3.1.2 и работает на лабораторной рабочей станции
под Windows 11 + WSL2. Результаты интерпретируются в [Scout](https://github.com/Clinical-Genomics/scout).

В репозитории нет данных пациентов, результатов анализа, референсных баз и учётных данных.
Коды образцов в комментариях и примерах заменены условными (`SAMPLE01` и т. д.).

---

## 1. Задачи

1. Диагностика редких наследственных заболеваний у пациентов Республики Саха (Якутия): поиск
   однонуклеотидных вариантов и инделов, структурных вариантов и CNV, экспансий повторов, вариантов
   митохондриальной ДНК, определение копийности *SMN1/SMN2*.
2. Обработка данных внутри лаборатории, без передачи геномных данных во внешние облачные сервисы.
3. Формирование популяционной базы частот аллелей якутской когорты для фильтрации вариантов,
   частых в популяции, но редких или отсутствующих в gnomAD.
4. Стандартизированная и воспроизводимая обработка образцов с автоматической архивацией результатов.

## 2. Архитектура

На вход подаются парные FASTQ (или BAM) коротких прочтений Illumina или MGI/DNBSEQ. Тип анализа
(полный геном, экзом, панель) задаётся параметром `analysis_type` и файлом целевых регионов. Текущие
настройки рассчитаны на полногеномные данные (WGS, ~30–40x).

```
FASTQ / BAM
  │
  ▼
WSL2 Ubuntu 24.04 + Docker ── nf-core/raredisease 3.1.2 (Nextflow, GRCh38)
  │  контроль качества и выравнивание: fastp → bwa-mem2 → MarkDuplicates
  │  SNV/инделы: DeepVariant → GLnexus
  │  структурные варианты и CNV: Manta, TIDDIT, CNVnator → SVDB
  │  повторы: ExpansionHunter + Stranger;  SMN: SMNCopyNumberCaller;  мтДНК;  мобильные элементы: RetroSeq
  │  аннотация: VEP 110 (dbNSFP, REVEL, SpliceAI, LoFtool, pLI, ClinVar), vcfanno (gnomAD), CADD
  │  ранжирование: genmod
  ▼
архив результатов (отдельный HDD) ──► Scout (MongoDB) + IGV
```

## 3. Рабочая станция и системная конфигурация

| Компонент | Значение |
|---|---|
| CPU | AMD Ryzen 9 9950X, 16 ядер / 32 потока |
| ОЗУ | 128 ГБ DDR5 |
| Диски | NVMe 4 ТБ (система, WSL с референсами и рабочими каталогами); HDD 13 ТБ (архив) |
| ПО | Windows 11, WSL2, Ubuntu 24.04, Docker Engine внутри WSL, Nextflow |

- `.wslconfig` (`raredisease-setup/windows/.wslconfig`): `processors=32`, `memory=116GB`, `swap=16GB`.
  По умолчанию WSL получает половину ОЗУ, а этого не хватает для индекса bwa-mem2.
- Лимит Nextflow: 30 CPU / 100 ГБ (`conf/local.config`). Остаток отведён ОС, Docker и Nextflow.
- Windows останавливает WSL вместе с запущенным анализом при закрытии последнего окна Linux. Поэтому
  в автозагрузке стоит скрипт `windows/startup/ubuntu_keepalive.vbs`, который поддерживает фоновый процесс WSL.

## 4. Референсные данные

Референсы хранятся в `/data/raredisease/references/grch38` (около 580 ГБ) и в репозиторий не входят.
Загрузка автоматизирована скриптами `raredisease-setup/scripts/download_references.sh` и `fetch_hub.sh`.

| Ресурс | Версия | Источник |
|---|---|---|
| Геном GRCh38 | no-alt analysis set | [NCBI](https://ftp.ncbi.nlm.nih.gov/genomes/all/GCA/000/001/405/GCA_000001405.15_GRCh38/seqs_for_alignment_pipelines.ucsc_ids/) |
| gnomAD (геномы) | v4.1 | [gnomAD downloads](https://gnomad.broadinstitute.org/downloads) (`gs://gcp-public-data--gnomad/release/4.1/vcf/genomes`) |
| gnomAD SV | v4.1 | [gnomAD downloads](https://gnomad.broadinstitute.org/downloads) |
| gnomAD мтДНК | v3.1 | [gnomAD downloads](https://gnomad.broadinstitute.org/downloads) |
| CADD | v1.7, предрасчитанные SNV и аннотации (архив 335 ГБ) | [CADD](https://cadd.bihealth.org/download) |
| VEP cache | Ensembl 110, merged | [Ensembl FTP](https://ftp.ensembl.org/pub/release-110/variation/indexed_vep_cache/) |
| Плагины VEP | — | [VEP_plugins](https://github.com/Ensembl/VEP_plugins) |
| dbNSFP | 4.9a | [dbNSFP](https://www.dbnsfp.org/) |
| REVEL | 1.3 | [REVEL](https://sites.google.com/site/revelgenomics/) |
| ClinVar | текущий выпуск | [NCBI ClinVar](https://ftp.ncbi.nlm.nih.gov/pub/clinvar/vcf_GRCh38/) |
| SpliceAI | маскированные оценки из состава аннотаций CADD 1.7 | см. ниже |
| Ранговые модели | Clinical Genomics, SNV v0.4, SV v0.2 | [nf-core/test-datasets](https://github.com/nf-core/test-datasets/tree/raredisease) |

Особенности подготовки:

- **Загрузка.** Объём около 1 ТБ при медленном институтском канале. gnomAD (Google Cloud Storage)
  загружался без VPN на полной скорости. Серверы CADD и Ensembl из лаборатории доступны только через VPN,
  и скорость падает при параллельных загрузках, поэтому они загружались по одному файлу. Часть хромосом
  gnomAD загружалась на втором ПК и переносилась на внешнем диске. Многочасовые загрузки запускались
  автономными цепочками с докачкой (`aria2c`, `wget -c`).
- **gnomAD** сжат до AF-only VCF для vcfanno (AF, AF_grpmax, AC, nhomalt, AF_eas) и tab-файла для
  фильтров конвейера (`scripts/make_gnomad_af.sh`). Из gnomAD SV удалены записи без AF, на которых падал SVDB.
- **SpliceAI.** Исходный файл Illumina требует регистрации, которая для лаборатории оказалась недоступна.
  Использованы маскированные оценки SpliceAI из аннотаций CADD, конвертированные
  `scripts/spliceai_from_cadd.sh` с пересопоставлением символов генов на Ensembl 110.
- **CADD.** ESM-модели нужно связать жёсткими ссылками из `esm/` в `GRCh38_v1.7/checkpoints/`,
  иначе при каждом запуске torch.hub загружает их заново.
- **Ранговые модели** взяты стоковые, без полей локальных баз (loqusdb, swegen), которых пока нет.

## 5. Распределение ресурсов по процессам

Стоковые ресурсные классы nf-core (`process_medium` 6 CPU / 36 ГБ, `process_high` 12 CPU / 72 ГБ) при
лимите 100 ГБ приводили к последовательному выполнению задач при простаивающем процессоре. Ресурсы
подобраны по фактическим пикам из trace-файлов Nextflow.

| Процесс | Стоково | Настроено | Обоснование |
|---|---|---|---|
| BWAMEM2_MEM | 12 CPU / 72 ГБ | 14 CPU / 40 ГБ | фактический пик ~29 ГБ; две дорожки выполняются параллельно |
| SAMTOOLS_MERGE | 2 CPU | 8 CPU | слияние BAM занимало ~1 ч |
| FASTP | 36 ГБ | 4 ГБ | фактически 1,6 ГБ |
| DEEPVARIANT | 12 CPU / 72 ГБ | 24 CPU / 56 ГБ | основной потребитель CPU |
| GLNEXUS | 12 CPU / 72 ГБ | 12 CPU / 32 ГБ | одиночный образец |
| TIDDIT_SV | 6 CPU / 36 ГБ / 8 ч | `-p 6 --skip_assembly`, 16 ГБ | локальная сборка зависала более 7 ч на перицентромерном сателлите chr5 |
| GENMOD (все шаги SNV) | 36 ГБ | 100 ГБ / 24 ч | на ~3 млн SNV нехватка памяти приводила к зависанию без сообщения об ошибке |
| CADD | 36 ГБ | 24 ГБ | ~1,5 ядра и 13–15 ГБ на фрагмент |
| ENSEMBLVEP_SNV | 36 ГБ | 16 ГБ | |
| ME_SPLIT_ALIGNMENT, RETROSEQ_DISCOVER | — | maxForks = 1 | множество мелких задач задерживало запуск DeepVariant |

Время обработки одного WGS ~35–40x составляет около 10,5–11 ч (до оптимизации 12,5 ч).
Наиболее длительные этапы: CADD ~3 ч, DeepVariant ~2 ч, MarkDuplicates ~2 ч, genmod ~1 ч.

**Образцы обрабатываются строго по одному.** Nextflow позволяет запускать несколько образцов параллельно,
но один WGS в пиковые моменты занимает почти весь ресурс машины: DeepVariant использует 24 из 30 CPU,
genmod до 100 ГБ ОЗУ, выравнивание 2 × 40 ГБ. При двух параллельных образцах задачи конкурируют за
память, что приводит к уходу в своп или к аварийному завершению процессов (в том числе к «тихим»
зависаниям genmod), а суммарная пропускная способность не растёт. Последовательная очередь даёт
предсказуемое время и стабильную работу. Архивация предыдущего образца идёт в фоне, пока считается следующий.

## 6. Хронология внедрения: проблемы и решения

| Этап | Проблема | Решение |
|---|---|---|
| Первый запуск | заготовки популяционных ранговых моделей и баз (ещё без данных) ломали genmod и SVDB | запуск со стоковыми настройками nf-core; популяционные компоненты включаются после набора когорты |
| Структурные варианты | записи gnomAD SV без AF прерывали SVDB | очистка базы |
| Ранжирование SNV | genmod зависал на часы после нехватки памяти | 100 ГБ на все шаги genmod |
| TIDDIT | зависание на chr5, превышение лимита 8 ч | `--skip_assembly`; SV формируются по Manta и CNVnator |
| DeepVariant | ошибка `Tmpdir does not exist` при заданном TMPDIR | TMPDIR не переопределяется |
| CADD | повторная загрузка ESM-моделей при каждом запуске | жёсткие ссылки в `checkpoints/` |
| SpliceAI | недоступен исходный файл Illumina | оценки из аннотаций CADD |
| Scout | сбой загрузки частичных оценок SpliceAI; без `.tbi` Scout загружал 0 вариантов без ошибки | исправление парсера при загрузке (`scout_load.sh`), проверка индексов |
| Архивация | `Cannot allocate memory` при копировании на HDD во время счёта следующего образца | повторные попытки и повтор в конце очереди |
| Производительность | стоковые ресурсы выстраивали задачи в очередь | настройки из раздела 5 |

На контрольных образцах подтверждено обнаружение известной микроделеции (~1,6 Мб) и известного
гетерозиготного SNV.

## 7. Эксплуатация

Команда `ngs` (меню `C:\NGS_pipeline\NGS.bat`, инструкция `manual/ngs_guide.html`):

| Команда | Действие |
|---|---|
| `ngs run КОД F/M/U` | запуск образца из `C:\NGS_pipeline\new_samples\КОД` |
| `ngs queue add КОД ПОЛ` / `start` / `stop` / `remove` / `list` | очередь образцов |
| `ngs status`, `ngs log КОД` | состояние прогонов и место на дисках |
| `ngs resume КОД` | продолжение остановленного прогона |
| `ngs archive КОД` | повтор архивации после сбоя |
| `ngs discard КОД` | удаление неудачного прогона (с подтверждением) |
| `ngs check` | проверка окружения |

После успешного прогона результаты копируются в `D:\data_annotated\<дата>_<код>_<пол>\{raw,processed}`,
сверяются по md5 и удаляются с системного диска. Выравнивания хранятся в BAM для просмотра в IGV.

Интерпретация ведётся в Scout, развёрнутом в отдельном WSL-дистрибутиве (см. `scout-setup/README_ru.md`).

## 8. Установка на другую рабочую станцию той же конфигурации

1. На исходной машине, когда нет активных прогонов, запустить `second_pc\EXPORT_OLD_PC.bat`. Система
   (Ubuntu с референсами и Docker-образами, Scout, `C:\NGS_pipeline`, настройки WSL) копируется на внешний диск.
2. На новой машине выполнить `wsl --install --no-distribution`, перезагрузиться и запустить
   `IMPORT_NEW_PC.bat` с внешнего диска.
3. Проверить окружение командой `ngs check`.

Обновление скриптов из репозитория:

```bash
cd ~/nefu_mmhg_arctic_genomes_pipeline && git pull
rsync -a raredisease-setup/ ~/raredisease-setup/
bash manual/install_ngs.sh
```

## 9. Планы развития

- Популяционные частоты якутской когорты: совместный генотипинг gVCF неродственных индивидов
  (`scripts/build_yakut_af.sh`, `build_yakut_svdb.sh`) и учёт частот в ранговой модели.
  gVCF DeepVariant сохраняются для каждого образца.
- Локальная база Loqusdb для учёта частот вариантов среди обследованных лабораторией.
- Клинический набор генов на основе OMIM morbid для `generate_clinical_set`.
- Приоритизация вариантов по фенотипу (HPO).
- Вызов CNV с помощью GATK gCNV после накопления достаточной выборки геномов.

## 11. Правила работы с данными

- В идентификаторах, путях и файлах используются только лабораторные коды образцов, имена пациентов не используются.
- Данные пациентов и результаты анализа не размещаются в репозитории и внешних сервисах.
- Лицензионные материалы OMIM используются только в научных целях и только внутри лаборатории.
- После архивации результаты хранятся на отдельном диске и не остаются на системном.
