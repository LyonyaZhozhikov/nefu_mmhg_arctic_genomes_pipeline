# Разбор сбоев: симптомы, причины, решения

Журнал реальных сбоев конвейера с диагностикой и способами решения. Коды образцов заменены
условными (`SAMPLE01` и т. д.). Время указано по Якутску (UTC+9).

Краткий список прочих проблем этапа внедрения см. в разделе 6 `README.md`.

## 1. CADD: Snakemake `clock skew problem` после зависания ПК (второй ПК, 2026-11-05)

### Симптом

Прогон падает на `ANNOTATE_CADD:CADD` (контейнер `clinicalgenomics/cadd-with-scripts:1.7.3`,
ветка инделов), в `.command.err`:

```
WorkflowError in rule join ...
Output .../case_X_indels.tsv.gz has older modification time than input .../case_X_indels.novel.tsv ...
This might be due to a clock skew problem
```

Разница времени модификации — около 2 секунд. Snakemake внутри CADD проверяет, что выходной файл
новее входного, и при обратном порядке mtime считает это ошибкой.

### Контекст

Ранее в тот же день, во время выравнивания образца, на ПК шли тяжёлые файловые операции
(копирование WGS с флешек на D: и перенос данных внутри D:). Система зависла (нехватка RAM / очередь
ввода-вывода), была выполнена жёсткая перезагрузка. Сбой CADD произошёл несколькими часами позже.

### Вероятная причина

**Вероятная, не доказанная:** рассинхронизация часов WSL2 с Windows. У WSL2 известна проблема дрейфа
системного времени виртуальной машины после сна, гибернации, зависания или сильной нагрузки на хост;
время в Linux отстаёт или «прыгает», и файлы получают mtime не в том порядке, в каком создавались.
Прямой связи с утренней перезагрузкой не установлено (после перезагрузки WSL стартует с актуальным
временем), но зависание и последующая высокая нагрузка — подходящие условия для дрейфа.

### Решение

1. Сравнить время в WSL и в Windows:

   ```bash
   date; powershell.exe -NoProfile -Command 'Get-Date -Format o'
   ```

2. Если есть расхождение — синхронизировать время WSL по Windows
   (`hwclock` в Ubuntu 24.04 под WSL2 недоступен):

   ```bash
   sudo date -s "$(powershell.exe -NoProfile -Command 'Get-Date -Format o' | tr -d '\r')"
   ```

3. Продолжить прогон:

   ```bash
   ngs resume SAMPLE01
   ```

   Задача CADD перезапускается в новом рабочем каталоге `work/`, старые mtime на неё не влияют;
   все уже завершённые этапы берутся из кэша `-resume`.

### Resume, пока идёт очередь

Если очередь (`ngs queue`) уже считает следующий образец, параллельный `resume` безопасен по памяти
только когда у очереди не идёт выравнивание (bwa-mem2 / MarkDuplicates занимают основную часть ОЗУ).
Можно поставить отложенный запуск в tmux: он ждёт 10 минут подряд без процессов выравнивания и
только потом выполняет `resume`:

```bash
tmux new -d -s r57 'n=0; while [ $n -lt 10 ]; do if pgrep -fi "bwa-mem2|markduplicates" >/dev/null; then n=0; else n=$((n+1)); fi; sleep 60; done; ngs resume SAMPLE01'
```

Проверить: `tmux ls`; подключиться: `tmux attach -t r57`. Имена сессий tmux сопоставляются по
префиксу — выбирайте уникальные имена.

### Профилактика

- Не выполнять тяжёлые файловые операции (копирование/перенос десятков-сотен ГБ) на том же ПК во
  время выравнивания; копировать данные между образцами или на другом ПК.
- Возможная доработка: периодическая синхронизация времени WSL по Windows (например, в скрипте
  keep-alive раз в 10–30 минут) или проверка расхождения `date` перед запуском/возобновлением прогона.
- После зависания или выхода из сна перед продолжением работы проверять время в WSL (шаг 1).

## 2. Повреждённые FASTQ на носителе поставщика (2026-11-05)

### Симптом

Прогон образца `SAMPLE02` (MGI/DNBSEQ, 16 файлов `*.fq.gz`) дважды падал на ранних шагах
(чтение FASTQ). `gzip` сообщал об ошибках CRC / неожиданном конце файла.

### Диагностика

Проверка целостности всех архивов — и копии в `new_samples`, и **оригиналов прямо на флешке
поставщика**:

```bash
for f in /путь/к/образцу/*.fq.gz; do gzip -t "$f" && echo "OK  $f" || echo "BAD $f"; done
```

Ошибки оказались на самой флешке поставщика, во всех файлах. То есть повреждение не связано
с копированием на ПК и не является ошибкой конвейера.

### Решение

- Запросить у компании-секвенатора повторную выгрузку данных **с контрольными суммами md5**,
  сверить md5 после скачивания и `gzip -t` до запуска.
- Удалить неудачный прогон (`ngs discard SAMPLE02`) и заново поставить образец в очередь
  (`ngs queue add SAMPLE02 M`).
- Исходную флешку сохранить до получения исправных данных (для претензии поставщику).

### Профилактика

Проверять каждый новый образец `gzip -t` (или md5 по списку поставщика) до постановки в очередь:
полная проверка 16 файлов занимает минуты, а упавший прогон — часы.
